## Overview

I had planned to hook up Spotify since the early days of building this blog, so here I'll write down what I learned and how I implemented it.

Spotify lets you use a huge amount of data for free. To take advantage of this lovely service, we first need
to go through a few steps:

1. Register an app on the Spotify developer dashboard
2. Authenticate your account
3. Hook up the APIs you need

> This post assumes you already have a Spotify account. If you haven't tried the service yet, why not give it a shot this time? 🎧

Before writing the API function logic, I thought about how to implement the data fetching. There were two options:

- Fetch data on the server using the `fetch API`
- Fetch data on the client (Tanstack-Query, SWR, useEffect, use ...)

I judged that real-time updates weren't strictly necessary and that this wasn't a case where data is needed after a user interaction, so I decided to fetch the data using the `fetch` function inside server components.

## 3. Hook up the APIs you need

After creating environment variables for the sensitive info, find the APIs that match the scopes listed above, then write the functions that make the fetch requests and generate the tokens you need.

### getAccessToken

Send a `post` request to the endpoint that returns tokens, injecting the client ID and client secret you got from the dashboard.
In the `body`, pass the `refresh_token` you got from the curl request.

```ts title="getAccessToken" {1-3, 5-8}
const BASIC_TOKEN = Buffer.from(
  SPOTIFY_CLIENT_ID + ":" + SPOTIFY_CLIENT_SECRET,
).toString("base64");

const body = new URLSearchParams({
  grant_type: "refresh_token",
  refresh_token: SPOTIFY_REFRESH_TOKEN!,
}).toString();

const getAccessToken = async () => {
  const res = await fetch("https://accounts.spotify.com/api/token", {
    method: "POST",
    headers: {
      Authorization: `Basic ${BASIC_TOKEN}`,
      "Content-Type": "application/x-www-form-urlencoded",
    },
    body,
  });

  const data = await res.json();

  return data.access_token;
};
```

Now you can use this access token to freely reach whatever info you want.
What I needed was the currently playing track, recently played tracks, and playlist info, so I created functions for those. I also added helper functions to extract only the information I need.

## Adding blurDataURL

For images imported statically from the `public` folder, Next handles all the optimization on its own, and if you pass the `placeholder="blur"` prop, it automatically
generates a placeholder. But images from Spotify are external data that Next can't access at build time, so you need to generate `blurDataURL` manually with a function like this:

```ts title="blurUrl.ts"
export const getBlurDataUrl = async (url: string) => {
  const res = await fetch(url, {
    cache: "force-cache",
  });
  const buffer = await res.arrayBuffer();
  return `data:image/png;base64,${Buffer.from(buffer).toString("base64")}`;
};
```

With this function, you get a blur effect while the image loads, plus a performance boost through caching.

## Problems I ran into

While implementing this, I misunderstood a few concepts and hit some problems.

### 1. The difference between dev and production environments

In Next 15, the default behavior of the `fetch` function is designed to fetch data from the server on every request (`auto no cache`).
But for `HMR`, which exists for DX, another caching layer called `serverComponentsHmrCache` was introduced.
This cache applies to every `fetch` request, even ones with the `cache: 'no-store'` option.
So by default new data should be fetched on every request, but because of the HMR cache, old data was reused even after I changed code (e.g. editing a component).

> `serverComponentsHmrCache` is reset when the page is refreshed or navigated away from.

No matter what cache options I added, I sweated quite a bit trying to figure out why I wasn't getting fresh data.

> The gist: in the dev environment every request is made fresh, but under HMR things get cached.

### 2. Implementing server-side code with a client-side mental model

You need an access token to make requests to Spotify's API endpoints. Early in the implementation, I wrote the function so that it requested a token on every request without any caching and injected it into the header.
As a result, the caching behaved differently from what I expected.

Thinking about it now, the reason is obvious. Since the auth token differs per request, the request headers differ every time too. That meant the cache key was newly generated each time, and I hadn't accounted for how HTTP caching normally works.

While writing the code, I assumed that the token would naturally be stored in some external storage. In other words, my mental model was client-side authentication: once issued, you save the token in **web storage** and reuse it until it expires.

That's why caching wasn't happening even after I added the `cache: "force-cache"` and `revalidate: number` options.

<Image
  src="/images/spotify/cache-skip.png"
  width={640}
  height={450}
  alt="cache skip"
/>

To fix this, I decided to try implementing a simple in-memory cache.
Here's how it works:

1. Create a `Map` to store the token info.
2. When a token is requested, check the cache first.
3. If a cached token exists, return it as is.
4. If it's not valid, request a new token and store it in the cache. (first request, token expiry)

```ts title="spotify.ts" {5, 8-12, 25-28}
const BASIC_TOKEN = Buffer.from(
SPOTIFY_CLIENT_ID + ":" + SPOTIFY_CLIENT_SECRET,
).toString("base64");

const tokenCache = new Map<string, TokenCache>();

export const getAccessToken = async () => {
const cachedToken = tokenCache.get(SPOTIFY_REFRESH_TOKEN!);

if (cachedToken && cachedToken.expiresAt > Date.now()) {
  return cachedToken.accessToken;
}

const res = await fetch("https://accounts.spotify.com/api/token", {
  method: "POST",
  headers: {
    Authorization: `Basic ${BASIC_TOKEN}`,
    "Content-Type": "application/x-www-form-urlencoded",
  },
  body,
});

const data = await res.json();

tokenCache.set(SPOTIFY_REFRESH_TOKEN!, {
  accessToken: data.access_token,
  expiresAt: Date.now() + data.expires_in * 1000,
});

return data.access_token;
};

```

### 3. The difference between traditional server-side rendering (SSR), static site generation (SSG), and incremental static regeneration (ISR)

- **SSR**

  With traditional SSR (cache opt-out, or when using Dynamic APIs), a new page is generated for every client request. This approach
  has the advantage of always showing the latest data, but the downsides are that it consumes a lot of server resources and introduces page loading time.
  What was happening above, with no caching and a request to the server every time, is what you'd call traditional SSR.

- **SSG**

  SSG, as the name suggests, generates static pages ahead of time at build time and serves them when requested. Since every page is pre-generated at build time, page loads are very fast,
  and there's no load on the server. The downsides are that handling dynamic content is hard, and so is serving personalized content.

- **ISR**

  ISR keeps the benefits of static generation while still validating and regenerating pages. It generates pages ahead of time at build time while setting a revalidation time. (Of course, the `On-demand` approach is also possible.)
  Until the set time passes, the generated page is shown, and once it has passed, the page is regenerated in the background and the new page is shown. You keep the fast speed of SSG while updating the data periodically.
  The downside is that the data may not be fully real-time. (The first request after the revalidation time elapses is served the cached page, and only requests after that see the new page.)

My blog was using SSG, and for the Spotify-related pages I used revalidation times to implement ISR.
So what exactly did I misunderstand?

That's right... I wrongly assumed that with ISR, data is fetched fresh on every user request. 🥺 In reality, with ISR the data request happens once when the static page is generated at build time, and then once more in the background on the first user request after the set revalidation time has elapsed.
Here's roughly how ISR works:

1. At build time: static pages are generated when the app is built, and data is requested
2. First request after the revalidation time elapses: the user is served the previously cached page, while the page starts regenerating in the background with new data
3. After regeneration completes: every user after that sees the newly generated page
4. When the revalidation time elapses again, the process above repeats

So the in-memory caching I wrote above was actually code based on a misunderstanding of how ISR works.
And the cache being skipped every time was just a quirk of the dev environment.
