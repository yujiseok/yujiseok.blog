[2025년 회고](https://www.yujiseok.blog/posts/2025)에서 AI 덕분에 확보한 여유를 어디에 쓸지 고민했었다.
에이전트가 코드베이스를 직접 수정하면서 손으로 구현하는 시간은 줄었는데, 그다음 내 시간을 어디에 써야 할지는 막연했다.

그러다 2026년 3월에 [크리에이터 멤버십](https://coloso.co.kr/membership) 프로젝트를 맡게 되었다.
고객이 상품을 살펴보고 결제하는 서비스와, 상품·주문을 관리하는 파트너 어드민의 프론트엔드를 함께 맡았다.
정기 결제하는 구독형과 단건 구매하는 세션형 상품의 결제·환불 흐름을 다루는 일이었다.

카드 결제 심사 일정에 맞춰 6월 24일에 열어야 했다. 준비할 화면은 **고객 서비스 20개, 어드민 34개**였고, 주어진 일정은 근무일로 약 75일이었다.
처음에는 이런 생각을 했던 것 같다.

> AI를 최대한 활용하면, 주어진 기간 안에 어디까지 해낼 수 있을까? 🧑‍🏭

화면 구현을 맡기면서 그 앞뒤로 반복하는 일도 정리해 봤다.
기획서를 읽고 티켓을 만들고, 구현이 끝나면 테스트와 QA, 배포를 진행했다. 매번 비슷한 순서였으니 스킬로 만들어 볼 수 있지 않을까 싶었다.

## 화면을 맡기기 전에 정한 것들

에이전트에게 여러 화면을 맡겨도 데이터 변경과 API 호출 방식은 일정했으면 했다. 코드의 구조부터 정해 뒀다.

- 고객 앱의 데이터 변경은 Server Action으로 모았다.
- 초기 화면에 필요한 데이터는 React Server Components(RSC)에서 불러왔다.
- 댓글과 좋아요에는 서버 응답을 기다리기 전에 화면에 반영하는 낙관적 업데이트를 썼다.
- 어드민은 [orval](https://orval.dev)로 OpenAPI 명세에서 타입과 API 호출 코드를 생성했다. 다시 생성한 타입과 화면 코드가 맞지 않으면 컴파일 단계에서 확인할 수 있었다.

이 구조는 에이전트가 읽는 작업 규칙에도 적어 뒀다.
어드민은 별도 디자인 시안이 없어서 shadcn과 Base UI로 직접 구성했다. 에이전트에게 구현을 맡길 것도 생각해서 고른 조합이었다.

구독형과 세션형 상품의 결제·완료·실패·환불 흐름은 직접 정했다. 정원이 있는 상품은 결제 직전에 남은 자리를 다시 확인하도록 했다.
합의한 결제·정원·환불 기준을 확인해 에이전트가 구현할 때 따르게 했다.

## 반복하던 일을 여덟 개의 스킬로

개발과 QA·운영에서 반복하던 절차를 Claude Code의 스킬 문서로 작성했다. 참고 자료와 작업 순서, 완료 조건을 적었다.
`/spec`, `/backlog` 등 아래 여덟 개는 직접 만든 스킬 이름이다. 필요할 때 불러 썼고, QA에서 수정할 일이 생기면 작업 시작과 마무리를 반복했다.
계획 검토와 배포처럼 내가 확인할 지점에서는 기다리게 했다.

### 1. 기획 문서 확인 (`/spec`)

`/spec`으로 피그마에서 읽을 화면을 정하고, 화면별 에이전트가 병렬로 동작과 상태를 정리하게 했다. 시안만으로 알 수 없는 내용은 질문으로 남겨 문서 맨 위에 모았다.
이 단계에서는 문서만 만들었다. 내가 읽고 더 확인할 내용을 살펴본 뒤 티켓을 만들었다.

### 2. 기능을 티켓으로 나누기 (`/backlog`)

`/backlog`는 기획 자료와 구글 시트의 기능 목록으로 티켓·일정 초안을 만들었다. 내가 범위와 일정을 확인하면 지라에 생성하게 했다.
결제나 환불은 여러 화면에 걸쳐 있어, 규칙이 빠지지 않도록 도메인별로 작업을 나눴다.

### 3. 작업 시작 준비 (`/start`)

티켓과 연결된 피그마 자료를 읽고 작업 계획을 남기게 했다. 재개된 작업은 이전 로그부터 읽게 했다.
다른 사람의 담당 티켓은 먼저 확인하고, 새 기능은 계획이 티켓 범위에 맞는지 검토한 뒤 구현을 시작하게 했다.

### 4. 구현과 작업 마무리 (`/done`)

인증은 쿠키로 통일하고, 기능은 테스트부터 쓰도록 했다. 에이전트가 구현하는 동안 나는 고객 서비스와 어드민의 결제·환불 동작이 앞서 정한 기준에 맞는지 살펴봤다.

`/done`은 해당 티켓의 변경만 커밋하고, **테스트를 통과해야 PR을 만들게 했다.** 열린 PR이 있으면 재사용했다.
개발 작업을 마치는 것과 QA를 통과한 뒤 최종 완료하는 것은 구분했다.

### 5. 개발 환경에 배포하기 (`/deploy`)

`/deploy`는 배포할 앱과 환경, 코드 버전을 확인하도록 했다.
공유 환경이라 내가 내용을 확인한 뒤 배포를 실행하고 결과를 추적하게 했다. 배포는 QA 감시 루프와 별도로 시작했다.

### 6. QA 전에 테스트 케이스 확인하기 (`/tc`)

QA에 넘기기 전에는 QA가 구글 시트에 작성한 테스트 케이스(TC)의 기대 결과를 따라 한 번 더 테스트했다.

- 로직·컴포넌트는 Vitest로 검증했다.
- 자동화할 화면 흐름은 Playwright로 검증했다.
- 시각 확인·실결제·외부 연동은 수동 확인으로 남겼다.

자동 테스트에는 TC 번호를 적어 원본과 연결했고, 케이스가 많으면 범위부터 정했다.

ego-browser로 화면을 움직여 보고, TablePlus MCP로 데이터베이스에 테스트 데이터를 넣어 필요한 상태도 준비했다. 구현된 화면이 기대한 대로 동작하는지 최대한 확인하려고 했다.

### 7. QA 티켓 확인과 수정 (`/qa-sweep`)

`/qa-sweep`은 시작할 때 내가 확인한 뒤 QA 하위 작업을 한 시간 간격으로 살폈다. 프론트엔드 작업이 분명한 티켓만 할당하고, 애매하면 프론트엔드와 API 저장소를 함께 읽었다. 그래도 판단하기 어려운 건 남겨 뒀다.

처음 정한 자동 수정 범위 안의 작은 작업은 `/start` → 수정 → `/done`으로 이어 갔다. 여러 건이면 한 건씩 처리하고, 재개된 티켓은 로그와 QA 실패 사유를 읽어 기존 브랜치에서 이어 갔다.
별도로 배포를 확인한 뒤 QA에 넘겼다. QA를 통과하면 완료하고, 실패하면 재개 사유에 따라 다시 작업했다.

### 8. 제품 릴리즈 준비하기 (`/release`)

`/release`는 아직 배포되지 않은 변경을 티켓 상태·릴리즈 버전과 대조하고, 포함 여부가 애매한 작업을 따로 살폈다.
내가 포함할 변경을 정하면 배포할 변경 목록을 작성하게 했다. 실제 배포는 이후 별도 절차로 진행했다.

## 어디까지 맡겨도 될까

자동 수정 범위를 정하면서 내가 직접 볼 일도 같이 정리했다.

- 백엔드 작업이거나 소관이 불분명한 티켓은 검토 대기로 남겼다.
- 재개 사유나 재현 정보가 부족한 QA 티켓도 검토 대기로 남겼다.
- 수정할 파일이 다섯 개를 넘거나 공용 컴포넌트·결제 로직을 건드리면 멈추도록 했다.
- 테스트 실패 원인을 한 차례 고친 뒤에도 통과하지 못하면 내가 다시 살폈다.
- 같은 티켓이 두 차례 연속 재개된 경우도 내가 다시 살폈다.

**결제·정원·환불은 사용자의 돈과 운영 기준에 영향을 주는 만큼, 합의한 내용을 직접 확인했다.**

## 6월 24일에 열고, 계속 고치기

6월 24일 카드 결제 심사 일정에 맞춰 고객 서비스와 파트너 어드민을 함께 열었다.
런칭 뒤에도 정원 마감과 결제 완료 뒤 화면 이동을 살펴봤다. 쿠폰·바우처를 서비스·어드민·백오피스에 적용하면서 할인 기준과 재구매·만료 조건도 확인했다.

### 상품을 보고 있는 동안 정원이 마감된다면

상품 목록이나 상세 화면을 열었을 때 자리가 남아 있었다고 해서, 결제하러 가는 순간에도 자리가 있을까?
런칭 뒤에 정원 마감을 다루면서 확인해야 했던 부분이다. 반대로 어드민에서 정원을 늘렸다면 화면에 남아 있는 마감 표시도 바뀌어야 했다.

구매 버튼을 누르면 서버에서 최신 마감 여부를 다시 조회하도록 했다. 마감이면 안내 모달을 보여 주고, 닫을 때 상품 목록으로 돌아가거나 현재 목록을 갱신했다.
서버에 결제 시작을 요청하는 `checkout`에서도 인원 마감 응답이 오면 결제를 이어 가지 않고 안내했다. 화면에서 미리 확인하는 동작과 서버의 최종 판정을 함께 살펴야 했다.

### 결제는 끝났는데 화면은 그대로였다

9월에는 결제가 끝났는데도 완료 화면으로 넘어가지 않는 문제를 고쳤다.
페이지를 이동시키는 코드가 있는데 왜 결제 화면에 그대로 남아 있을까?

원인을 보니 결제대행사(PG)의 결제창이 브라우저의 이동 이력을 쌓고 있었다. 결제창이 닫힐 때 그 이력이 되감기면서, 진행 중이던 `router.push`가 취소되는 상황이었다.
Next.js 안에서 페이지를 이동시키던 처리를 `location.replace`를 통한 브라우저 직접 이동으로 바꿨다. 이동 방식만 간추리면 다음과 같다.

```ts
window.location.replace(path);
```

결제창의 이력 정리가 진행 중인 라우팅을 취소하지 않게 하고, 완료 뒤 뒤로가기로 결제 화면에 돌아가는 것도 막기 위해서였다.

예전에 [네비게이션 개선 글](https://www.yujiseok.blog/posts/improve-navigation)에서는 전체 새로고침을 줄이려고 고민했는데, 이번에는 브라우저에서 직접 이동하도록 바꾸며 문제를 해결했다.
같은 페이지 이동이어도 결제창이 끼어드니 함께 봐야 하는 동작이 제법 달랐다.

## QA 기록을 돌아보니

고객 서비스와 어드민에서 내 담당 QA 티켓은 116건이었다. 기능 버그, 디자인 불일치, 추가 요구가 섞여 있어 내용별로 나눠 봤다.

| 구분 | 어드민 | 멤버십 고객 서비스 | 합계 |
| - | - | - | - |
| 동작·노출·저장이 기획과 달랐던 기능 버그 | 32 | 27 | 59 |
| 크기·색·정렬 등 디자인 가이드와의 불일치 | 0 | 20 | 20 |
| QA 중 추가된 요구 | 21 | 15 | 36 |
| 수정 없이 닫은 티켓 | 1 | 0 | 1 |
| 합계 | 54 | 62 | 116 |

기능 버그 59건과 디자인 불일치 20건을 합치면 구현 이슈는 79건이었다.
지라의 티켓 유형인 Defect에는 디자인 수정이나 개선 요청도 섞여 있어서, 위 표에서는 실제 수정 내용을 기준으로 나눴다.

어드민은 별도 시안 없이 구성했으므로, 디자인 불일치 0건을 고객 서비스의 20건과 같은 기준으로 비교하기는 어렵다.

## 이전에 만든 포트폴리오와 비교해 보기

이전에 만들었던 [포트폴리오](https://www.yujiseok.blog/posts/how-to-implement-portfolio)는 어땠을까 싶어 기록을 나란히 놓아 봤다.

여기서는 두 고객 화면의 신규 구현 1차 QA를 비교했다. 앞의 고객·어드민 합계 116건과는 범위가 다르다. 코드량도 각 1차 QA 당시를 기준으로 잡았다.

| 구분 | 포트폴리오 1차 QA | 멤버십 1차 QA |
| - | - | - |
| QA 기간 | 2025-05-16 \~ 06-11, 26일 | 2026-06-02 \~ 06-22, 20일 |
| 당시 화면 코드 | 74개 파일, 3,636줄 | 135개 파일, 9,107줄 |
| 전체 QA 티켓 | 126건 | 68건 |
| 그중 Defect 타입 | 69건 | 40건 |
| 내 담당 Defect 타입 | 31건 | 34건 |
| 화면 코드 1,000줄당 내 담당 Defect | 약 8.5건 | 약 3.7건 |
| 내 담당 Defect 한 건당 화면 코드 | 약 117줄 | 약 268줄 |

내 담당 Defect는 포트폴리오 31건, 멤버십 34건으로 비슷했다. 그 사이 화면 코드의 규모는 3,636줄에서 9,107줄로 약 2.5배가 되었다.

Defect 한 건당 코드량으로 보면 117줄에서 268줄로 약 2.3배였다. **발견된 Defect 수가 비슷한 상태에서 더 큰 구현 범위를 다루게 된 셈이다.**

두 프로젝트 모두 지라의 Defect 타입으로 맞췄다. 멤버십 34건에는 기능 버그 27건, 디자인 불일치 6건, 개선 요청 1건이 포함된다. 포트폴리오 31건은 기능과 디자인으로 다시 나누지 않은 값이다.

기능도 다르고 QA 기간도 달라서, 이 숫자만으로 AI의 효과를 딱 잘라 말하기는 어렵다. 멤버십에서는 에이전트에게 구현과 검증을 함께 맡겼고, 이전보다 넓은 범위를 진행할 수 있었다.

## 멤버십을 만들고 나서

처음 멤버십을 맡았을 때는 '이걸 혼자서 어떻게 하라는 거지' 싶었다. 고객 서비스에 어드민까지, 정해진 기간 안에 만들어야 한다니 솔직히 화도 좀 났다.

그러다 이왕 이렇게 된 거, AI를 최대한 써보자는 생각이 들었다. 반복하던 일을 스킬로 만들고, 작업 순서와 내가 확인할 부분을 하나씩 정리했다. 그렇게 해본 게 이번 일정을 맞추는 데 꽤 도움이 됐던 것 같다.

예전에도 AI는 쓰고 있었는데 일정이나 마감이 부담스러운 건 여전했다. 이번에는 일하는 방식을 한 번 정리하고 나니 그 압박이 많이 줄었다. 다음에 또 큰 프로젝트를 맡아도 이번처럼 일을 나누고 AI를 활용하면 일정 안에 끝낼 수 있겠다는 자신감도 생겼다.
