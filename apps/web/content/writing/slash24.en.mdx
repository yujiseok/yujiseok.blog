## N tabs, a single WebSocket: SharedWorker

This session walked through how Toss Securities solved the problems that came up when it expanded from mobile-only to desktop.

### The problem the Toss team faced

Toss Securities was originally a mobile service, and when it started supporting desktop, there were new problems to solve.
The Toss team was using WebSocket to get real-time securities data.

#### What is a WebSocket?

A WebSocket is a protocol that enables real-time, two-way communication between a client and a server.
Unlike regular HTTP, a WebSocket keeps a persistent connection open so the client and server can keep exchanging data.
It's especially well suited to services that need real-time data. (e.g. chat, stock trading)

A simple WebSocket connection looks like this:

```ts
const socket = new WebSocket("ws://localhost:8080");

socket.addEventListener("open", () => {
  console.log("웹소켓 연결 성공!");
});

socket.send("데이터 전송!");

socket.addEventListener("message", (e) => {
  console.log("서버로부터 메시지 수신: ", e.data);
});
```

So what problem came up that the Toss team had to solve?
The biggest difference between a mobile app and a desktop environment is that on desktop, when you open several tabs in a browser, each tab runs independently.
Each tab being independent means each tab has its own WebSocket connection.

What happens when you end up with independent WebSockets like this?
Because every tab is independent, many WebSocket connections get created between the server and the clients, which puts load on the server.
In other words, server resources get wasted. For developers who hate duplication and love reuse, this is an absolute horror show. 🫨

So how did the Toss team get out of this situation?
They first considered approaches that cut the connection, like these:

1. focus / blur events
   - Create the WebSocket connection only when a tab is active, and close it when the tab is inactive
   - Problem: data can only be received while the tab is active, which hurts the user experience

2. visibilitychange event
   - The visibilitychange event fires when the visibility of a web page changes
   - Create and close the WebSocket connection every time the user switches tabs
   - Problem: you still get as many WebSocket connections as there are visible tabs

Neither of these approaches solved the root problem of WebSockets being created independently.

### The solution

Since cutting connections couldn't fix the root problem, they had to find a new solution.
The fundamental fix was to find a way for every tab in the browser to share a single WebSocket connection, like in the picture below.

To stop WebSockets from being created and connected independently for every tab, the Toss team adopted **SharedWorker** from the [**Web Workers API**](https://developer.mozilla.org/ko/docs/Web/API/Web_Workers_API).

#### Web Workers API

The Web Workers API is a browser API that lets you run scripts in a separate background thread, apart from the main execution thread.
JavaScript is designed to be single-threaded, so it can only do one thing at a time. With a web worker, you can run work in a separate background thread.

The JavaScript file you designate as a worker runs in a worker thread, which has a global context completely different from the window.
However, not everything can be run in a worker thread. You can't manipulate the DOM from a worker thread, and some methods and properties of the window object aren't available.
WebSocket, though, can be used in a worker thread. The worker and the main thread exchange data using a messaging system.

A worker used by a single script is called a Dedicated Worker, and a worker used across multiple browsing contexts is called a Shared Worker.

- Dedicated Worker
  - Single connection: it can only be accessed from one script, and can only communicate with the script that created it.

- Shared Worker
  - Multiple connections: it can be accessed from multiple tabs, and multiple scripts within the same domain can share that worker instance.
  - Cross-tab communication: tabs can send messages to each other, so multiple tabs can share the same data or keep the same state.

As you can see above, with a SharedWorker, tabs can exchange data through a single WebSocket. SharedWorker supports communication between tabs through the `Channel Messaging API`.
This API uses `MessageChannel`'s port, `MessagePort`, to let you send messages between different ports.

So data can now be shared in real time in the shape of **tab - SharedWorker + WebSocket - server**.
They also made it so that in browsers that don't support SharedWorker, a Dedicated Worker is used as a fallback.

#### Challenges in the actual implementation

1. Bundling

When specifying the path to the web worker file, using a relative path caused the bundler to fail to find the file.
Here's how to get around that:

```ts
const worker = new SharedWorker(new URL("./worker.ts", import.meta.url));

// 변환

const worker = new SharedWorker(new URL("./chunks/q1w2e3r4.js"));
```

2. Memory leaks

When a tab was closed, the SharedWorker instance stayed in memory.
The `BeforeUnload` event, which fires when a tab closes, isn't called if you close the tab while it's minimized.
To solve this, they said they combined `WeakRef` with `MessagePort` to detect tab closing using garbage collection.

When a tab closes, its MessagePort gets garbage collected and released from memory.
But the SharedWorker keeps its MessagePort objects in an array, so garbage collection never happened.

They fixed this by using `WeakRef` so that garbage collection could happen.
WeakRef provides a weak reference to an object, allowing it to be cleaned up by the garbage collector.

The WeakRef syntax looks like this:

```ts
const obj = { name: "Ye" };
const weakObj = new WeakRef(obj);

if (!weakObj.deref()) {
  console.log("객체가 메모리에서 해제되었습니다.");
}
```

They manage the connected ports with WeakRef, and when a tab closes, those ports get released, which prevents the memory leak.

### Dev chat

The dev chat was a networking program where you could get closer to the speakers who had given the sessions.
Through it, I could ask the speakers questions and have deeper conversations.
I was curious how they validated the technology while solving a problem like this, so I asked about that.
I was told that since there were almost no examples of sharing a WebSocket across tabs with SharedWorker, they validated it by referring to the [W3C](https://www.w3.org/TR/2021/NOTE-workers-20210128) spec and MDN.

The domain I work on isn't a service that mainly relies on real-time communication,
but the process of identifying the problem and then finding the solution really impressed me.
Understanding the root problem and then bringing in new technology to solve it was inspiring to me as a developer.
