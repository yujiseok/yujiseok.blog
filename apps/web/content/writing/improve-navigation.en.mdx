## Overview

I'll walk you through my thought process, starting from a simple question about why something behaves the way it does and ending with an actual feature improvement.

While exploring our service's pages as if I were a customer, I kept running into a frustrating behavior on certain pages: a full page refresh.
I had assumed navigation would naturally be client-side, so running into unexpected behavior made me want to fix it.

It bothered me so much that I kept muttering "ugh, I really want to fix this..." while putting it off with the excuse of other issues. Half a year went by, and I finally couldn't look the other way anymore.

## Identifying and Defining the Problem

As I moved between pages, the client-side navigation I took for granted wasn't working. So I started asking "why?"
With a modern framework (library) like **Next**/**React**, navigation within the app should generally be client-side, but on our service it was running as server-side navigation, and that was the problem.
So I decided to dig into the cause of this unexpected behavior.

To find it, I first had to look at how the pages are put together.
The process goes like this:

1. Pages are managed in a CMS (content management system) format
2. The page's HTML data is returned as a string
3. The returned HTML string is converted into a DOM tree with a DOM parser, followed by post-processing that adds the necessary scripts
4. If extra work (dependent on React) is needed, the layout is replaced with a matching React component and rendered
5. If no extra work is needed, the original HTML is injected with the `dangerouslySetInnerHTML` prop and rendered

In this process, the script that controls client-side navigation was missing, which led to a structural problem: page transitions were forced into server-side navigation (a full page refresh).
On top of that, some layouts didn't use anchors for navigation at all, but handled it programmatically with button tags.

Now I knew what the problem was. Next, I set out to decide how to fix it.

## Direction for the Fix

From the moment I understood the problem, I decided to fix it by turning the affected layouts into React components.

## Fixing It by Replacement

That's because I figured I only needed to handle the case where the layout used on the event page does programmatic navigation directly with button tags.

Then I tried to build a new component that maps the layout to the `Link` provided by Next.
The layout I wanted to replace (101) is like a blank canvas that users can freely compose, and everything, including inline styles and actual styles, comes back as HTML data.

### 2. Do I Have to Follow Replacement?

I found out that there are several ways to do replacement.

1. `dangerouslySetInnerHTML`

   - This is the simplest method, but I judged it unsuitable for handling scripting
   - It also has security vulnerabilities, so personally it's not a method I like

2. Using an HTML parsing library

   - A parsing library can convert the string-based structure into plain HTML tags or components
   - However, adding the library would need another round of verification, and since adding a dependency is something our team avoids, it might well have been rejected
   - The setup isn't complicated, so it was appealing, but I wanted to solve this myself, so it was my last resort

3. Using a custom component

   - This is the one I actually tried, and 1:N mapping is hard with it

What other approaches are there besides replacement? Am I missing something? As my thinking shifted naturally, I started looking into what navigation methods my framework provides.

### 3. Navigation Methods Provided by the Framework (Next)

- `Link`

  - The solution that fit my original idea of replacement
  - Extends the `a` tag to provide prefetching and client-side navigation
  - Using this component makes improving navigation very simple → I thought this would work, but..!
  - Next officially recommends using the `Link` component unless you have specific requirements

- `useRouter`

  - Unlike the `Link` component, this is a built-in Next hook that lets you handle navigation programmatically
  - In other words, it changes routes programmatically
  - **Specific requirements** → this answered the question I'd been trying to resolve
  - A hook that controls the browser's History API

## The Actual Fix (Intercepting Navigation with useRouter)

Putting all of the above together, I had specific requirements to deal with, so using the `useRouter` hook looked like the simplest way to fix this.
Then I thought about how I could apply navigation with that hook, based on these situations:

- When the HTML tag is an anchor tag
- When programmatic navigation is applied to a tag that isn't an anchor

### When It's an Anchor Tag

First, find the anchor tag. Then grab its `href` attribute and validate that `href`.

- External links
  - If it starts with https, client-side navigation isn't needed, so do nothing.
- Internal links
  - For internal links, prevent the anchor tag's default behavior.
  - Then use the `router` object created with the `useRouter` hook to navigate programmatically to the `href` found above.
- Links whose href includes the origin URL
  - For example, when the `href` set in the CMS is `href="https://coloso.co.kr/...`
  - If it includes the origin URL, add extra condition handling.

### When Programmatic Navigation Is Applied to a Non-Anchor Tag

I tried to cover every HTML tag case, but eventually concluded that handling every case was too hard.
So after discussing it with the CMS operators, we agreed to use anchor tags, the tag that semantically plays the role of moving between pages.

Thanks to this, I could solve the problem by handling only anchor tags, with no additional code.

### Implementing the `useRouteInterceptor` Custom Hook

I decided to build a custom hook that intercepts navigation across all of the HTML. Using this hook has the following benefits:

- No need to handle individual HTML attributes and tags
- No need for 1:1 mapping per layout
- Navigation for pages composed in the CMS can be controlled from a single hook

```ts title="useRouteInterceptor"
const useRouteInterceptor = () => {
  const router = useRouter();

  const interceptAnchorClick = (e: MouseEvent<HTMLElement>) => {
    const anchor = (e.target as HTMLElement).closest('a');
    const href = anchor?.getAttribute('href');

    if (shouldBypassRouter(href)) return;

    e.preventDefault();

    const path = extractPath(href);
    router.push(path);
  };

  return { interceptAnchorClick };
};

export default useRouteInterceptor;

```

The `interceptAnchorClick` function returned by the hook is implemented to control events from a parent element through event delegation. Here's how it works:

1. When a component is clicked, extract the target info from the event object
2. Find the anchor tag closest to the target
3. Extract the anchor tag's `href`
4. If there's no `href` or it's an external link, client-side navigation isn't needed, so the function exits
5. If an internal page transition is needed, prevent the anchor tag's default behavior
6. Then use Next.js's `router` to implement client-side navigation

A hook of fewer than 20 lines of code solved the problem effectively.

### Differences in Network Request Patterns

Before the fix, each navigation triggered multiple network requests, and you can see DCL (DOMContentLoaded), FP (First Paint), FCP (First Contentful Paint), and so on firing again and again.
This means the entire page lifecycle restarts with every page transition. After the fix, the pattern changed to requesting only the data that's needed, and the network load dropped significantly.

### Results After Switching to Client-Side Navigation

- Faster page transitions reduce users' waiting time
- Since the whole page isn't reloaded, users get a smooth experience without screen flicker
- Only the necessary data is loaded, so network traffic goes down → server load goes down
- Stable heap memory usage

### Conclusion

The metrics make the performance improvement clear.
By switching from server-side to client-side navigation, total loading time dropped by about **46%**,
and scripting time (**78.3%**) and rendering time (**72.1%**) fell dramatically. This shows that the user experience during page transitions improved a great deal.
